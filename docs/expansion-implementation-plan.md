# 캠퍼스 플랫폼 확장 구현 계획

기존 녹색·베이지 전체 조감도와 16개 건물·개념 내부도를 유지한다. 확장 기획 32개 항목을 등록 데이터, 공개 탐색, 모델 공급자, 운영 API, 관리 화면, 배포·검증으로 연결한다.

## 목적과 데이터 흐름

자료/모델 → 스키마·출처·공간 참조 검증 → 초안 → 검토/승인 → 불변 공개판 → 같은 공간 ID를 사용하는 3D·2D·문자 검색/투어/공유. 운영기간·통제는 별도 승인 자료로 연결한다. 실제 제공되지 않은 호실 치수, 법적 경계, 현장 통행, 학교 API·실시간 데이터는 미확인/미연결로 유지한다.

## 구현 순서

1. 공간 ID·캠퍼스·복수 경계·근거·버전 계약과 기존 자료 변환, 순수 검색/경로/운영/상태 도메인.
2. 단일 모델 등록, 기본 부지 우선 렌더, 부분 로딩/실패, 정밀 모델 adapter, 시점·자원 복원.
3. 공개 UI: 공간 탐색·2D/문자·공유/QR·개인 저장/시간표·가상 투어·검증 경로·제보·자료 전환.
4. SQLite 마이그레이션, 비공개 역할/세션·CSRF, 초안/승인/공개/복구, 제보·운영 기록·감사·상태 API와 관리자 화면.
5. 원자적 공개 자료 배포, 선택적 오프라인 캐시, 로컬 라이브러리, 운영 문서/CI/컨테이너·검증.

## 영향과 위험

bootstrap/장면은 모델 등록 공급자로 전환하되 현재 모델의 비율과 자료 확인 수준을 유지한다. 도메인·UI·API는 공간 ID로 연결한다. 공개 allowlist를 새 런타임/자산 목록으로 확장하며 원자료·DB·관리 기록을 정적 공개 파일에 넣지 않는다. 초기 SQLite 단일 서버 운영 범위를 명시하고 DB를 공개판과 분리한다. 학교 API와 실측 자료를 확보하지 않은 기능은 등록·검증·실행 경로 및 미연결 상태까지 제공한다.

## 검증과 복구

lint/typecheck/unit·DOM·모델·HTTP·SQLite integration/build/generated sync, desktop/mobile 실제 Chromium 핵심 흐름, 실패 자산·오래된 정보·CSRF/역할·동시수정 충돌·승인 전 공개 제한·공개판 복구를 검증한다. 현장 경로/실측·보조기술 사용자·실기기 성능·실학교 API 검증은 별도 미검증으로 기록한다.

운영 데이터는 초기화하지 않는다. 마이그레이션은 추가 파일로 적용하며 공개판은 불변 기록과 current pointer로 관리한다. 승인된 이전 공개판 복구 및 SQLite 온라인 백업을 제공한다. 이전 버전 프로그램으로 되돌릴 때는 호환 DB와 백업을 유지하고 기존 사용자 변경을 되돌리지 않는다.
